⟲ linback Linux-Server-Backup & Restore

1 · Mit dem Server verbinden & analysieren

Was passiert in diesem Schritt?
  1. Die App öffnet eine SSH-Verbindung zu deinem Server. Beim ersten Mal zeigt sie den Fingerabdruck des Server-Schlüssels; du bestätigst ihn (wie bei ssh im Terminal). Ändert er sich später, wirst du gewarnt.
  2. Dann läuft ein kurzes, rein lesendes Shell-Skript (unten einsehbar). Es installiert nichts, schreibt nichts und ändert nichts auf dem Server.
  3. Es sammelt: Betriebssystem & Kernel, CPU/RAM, Boot-Modus (UEFI oder BIOS), Platten & Mountpoints mit belegtem Platz, RAID/LVM, fstab, Netzwerk (netplan), vorhandene Werkzeuge (tar, zstd) und laufende Dienste (Datenbanken, Docker).
  4. Daraus berechnet die App, was gesichert wird (nur echte lokale Dateisysteme wie ext4/xfs/btrfs — kein /proc, /sys, NFS, tmpfs), wie groß das Backup etwa wird und welche Risiken es gibt (z. B. laufende Datenbanken).

Dein Passwort bleibt nur im Arbeitsspeicher dieser App und wird nie gespeichert. Empfohlen: Anmeldung als root mit SSH-Schlüssel — nur dann sind alle Dateien lesbar.

2 · Backup erstellen

  

    Was passiert in diesem Schritt?
    
    
      
  1. Optional: Ein von dir angegebener vorbereitender Befehl läuft zuerst auf dem Server (z. B. ein Datenbank-Dump), damit die Daten konsistent sind.
    2. 
      
  2. Auf dem Server startet GNU tar und liest / sowie alle weiteren lokalen Dateisysteme. --one-file-system verhindert, dass /proc, /sys, NFS-Freigaben oder tmpfs mitgelesen werden. Gesichert werden Besitzer (numerisch), Rechte, ACLs, erweiterte Attribute, Symlinks, Hardlinks und Sparse-Dateien.
    3. 
      
  3. Der tar-Strom wird auf dem Server komprimiert (zstd, sonst gzip) — mit niedriger Priorität (nice/ionice), damit laufende Dienste nicht leiden.
    4. 
      
  4. Der komprimierte Strom läuft verschlüsselt durch die SSH-Verbindung direkt in eine Datei auf deinem Rechner (system.tar.zst.enc.partial). Es wird nichts auf dem Server zwischengespeichert. Dabei wird live eine SHA-256-Prüfsumme berechnet.
    5. 
      
  5. Archiv-Verschlüsselung (empfohlen): Auf deinem Rechner wird der Strom zusätzlich mit AES-256 verschlüsselt; der Schlüssel wird per PBKDF2 (600 000 Runden) aus deiner Passphrase abgeleitet. Das Format ist openssl-kompatibel — du kannst es notfalls auf jedem Linux ohne diese App entschlüsseln. Zusätzlich wird ein HMAC im Manifest abgelegt, der bei der Wiederherstellung vor dem Löschen prüft, dass Passphrase und Datei stimmen. Der Server sieht die Passphrase nie.
    6. 
      
  6. Am Ende wird die Datei umbenannt und es entstehen manifest.json (Prüfsumme, Quelle, Ausschlüsse), system-info.json (Analyse) und eine Kopie des linback-restore.sh-Skripts — der Ordner ist also auch ohne diese App wiederherstellbar.
    7. 
    

    
Bewusst nicht im Backup: Partitionstabelle, Bootloader, UUIDs und MAC-gebundene Netzwerk-Regeln. Genau deshalb ist das Backup hardwareunabhängig: Das alles wird erst bei der Wiederherstellung passend zur Zielhardware neu erzeugt.

    
Ohne Verschlüsselung enthält das Archiv /etc/shadow, SSH-Schlüssel und alle Daten im Klartext. Mit Verschlüsselung gilt: Geht die Passphrase verloren, ist das Backup unwiederbringlich verloren — sie wird nirgends gespeichert.

3 · Backup prüfen

  

    Was passiert in diesem Schritt?
    
    
      
  1. Die App liest manifest.json aus dem Backup-Ordner.
    2. 
      
  2. Sie liest das Archiv komplett von der Platte und berechnet erneut die SHA-256-Prüfsumme. Sie wird mit dem Wert verglichen, der beim Download berechnet wurde. So erkennst du defekte Datenträger, abgebrochene Kopien oder Manipulation bevor du im Ernstfall darauf angewiesen bist.
    3. 
      
  3. Bei verschlüsselten Backups prüft die App mit deiner Passphrase zusätzlich den HMAC: So erkennst du, ob die Passphrase stimmt und ob jemand das Archiv gezielt verändert hat (die einfache Prüfsumme könnte dann mitgefälscht sein). Ohne Passphrase wird nur die Prüfsumme geprüft.
    4. 
      
  4. Es wird nichts verändert und keine Verbindung zum Server aufgebaut.
    5. 
    

    
Tipp: Prüfe wichtige Backups nach jedem Kopieren (USB-Platte, NAS, Cloud). Die Wiederherstellung führt dieselbe Prüfung automatisch aus, bevor Platten gelöscht werden.

  

  

    
    
    
 

  

  

  







  
4 · Auf neuer/leerer Hardware wiederherstellen

  

    Was passiert in diesem Schritt? (Hetzner Rescue-System)
    
Du brauchst kein Installationsmedium. Das Rescue-System ist ein kleines Linux, das der Server über das Netzwerk bootet — dein Zielserver läuft dann nicht von seinen eigenen Platten, die daher frei beschreibbar sind.

    
Vorbereitung bei Hetzner (Robot): Server wählen → Reiter Rescue → Linux (64 bit) → Aktivieren (Passwort notieren, optional SSH-Schlüssel hinterlegen) → Reiter Reset → Automatischen Hardware-Reset auslösen. Nach 1–2 Minuten ist der Server per SSH als root erreichbar. Beim neuen Rescue-System ändert sich der Host-Schlüssel — die App fragt dann nach.

    
Danach läuft die Wiederherstellung in diesen Phasen — jede wird unten live angezeigt:

    
    
      
  1. Archiv prüfen: SHA-256 des Backups gegen das Manifest, bei verschlüsselten Backups zusätzlich der HMAC (falsche Passphrase fällt hier auf). Bei Fehler wird nichts gelöscht.
    2. 
      
  2. Verbinden & Skript hochladen: linback-restore.sh wird nach /tmp des Rescue-Systems kopiert.
    3. 
      
  3. Werkzeuge: Fehlende Programme (sgdisk, mdadm, zstd, …) werden per apt nachinstalliert.
    4. 
      
  4. Platten vorbereiten (LÖSCHT DATEN): Alte RAIDs/Mounts lösen, Platten mit wipefs/sgdisk --zap-all leeren, neue GPT-Partitionen anlegen, ggf. Software-RAID1 erzeugen, ext4 + Swap (+ EFI-Partition) formatieren und nach /mnt/linback-target einhängen.
    5. 
      
  5. Archiv entpacken: Die Archivdatei wird (bei Verschlüsselung lokal auf deinem Rechner entschlüsselt und dann) direkt durch SSH gestreamt und on-the-fly entpackt (zstd -d | tar -x). Das Rescue-System hat nur wenig RAM; deshalb wird nichts zwischengespeichert.
    6. 
      
  6. System an die Hardware anpassen (per chroot): neue /etc/fstab mit den neuen UUIDs · mdadm.conf · alte MAC-/Interface-Bindungen entfernen · Netzwerk neu schreiben · fehlende Boot-Pakete installieren · initramfs mit allen Treibern (MODULES=most) neu bauen · GRUB für BIOS oder UEFI (inkl. Fallback-Pfad EFI/BOOT/BOOTX64.EFI, falls das Mainboard den Boot-Eintrag nicht kennt) installieren · update-grub.
    7.

    5 · Boot-ISO / Restore-Paket (optional)
    
  
    
    Was passiert in diesem Schritt?
    
    Wann brauchst du das? Bei Hetzner meist nicht — das Rescue-System (Schritt 4) ersetzt ein ISO. Ein ISO ist sinnvoll, wenn der Server nicht per Netzwerk booten kann, du über die KVM-Konsole mit einem virtuellen Medium arbeitest oder eine Restore-Umgebung offline (USB-Stick) bereithalten willst.
    
    
      
      
    1. Restore-Paket: Die App legt einen Ordner mit linback-restore.sh, einer Anleitung und (optional) deinem Archiv an. Das reicht, um in jedem Linux-Live-System wiederherzustellen.
      2. 
      
    2. Bootbares ISO: Du wählst ein Debian-/Ubuntu-Live-ISO als Basis (z. B. debian-live-…-standard.iso von debian.org — die App lädt nichts selbst herunter). Mit xorriso wird dieses ISO unverändert kopiert (inkl. BIOS- und UEFI-Boot) und um den Ordner /linback ergänzt. Es entsteht kein neues Betriebssystem, nur dein Live-System plus Restore-Werkzeug.
      3. 
      
    3. Im gebooteten Live-System startest du bash /run/live/medium/linback/linback-restore.sh wizard; das Skript fragt Platten, Layout und Netzwerk ab und führt dieselben Phasen wie Schritt 4 aus.
      4. 
    
    
    
    Ein ISO mit eingebettetem Archiv wird so groß wie dein Backup. Bei sehr großen Servern ist ein kleines ISO plus Archiv auf USB-Platte/NAS praktischer. Das ISO-Bauen benötigt xorriso (macOS: brew install xorriso; Windows: in WSL).
